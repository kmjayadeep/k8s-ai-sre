Incremental Scaling Plan

Start by splitting the core responsibilities inside the same container. This creates clean boundaries without introducing Kafka/NATS, Postgres, separate workers, or a multi-cluster agent too early.

One container One FastAPI deployment Same SQLite store for now Same synchronous investigation flow Clear internal components

Current decision

Do not refactor immediately into a distributed architecture. First make the app a modular monolith: separate ingestion, investigation, notification, approval, and execution boundaries while keeping runtime behavior unchanged.

Phase 1 architecture: split components, same container

The external shape remains simple. Internally, each domain gets a clear owner.

Introduce external queue, separate deployments, LLM gateway, executor workers, and multi-cluster agents.

Do not do yet

  • Do not introduce Kafka/NATS/SQS immediately.
  • Do not split into many Kubernetes Deployments yet.
  • Do not migrate to Postgres as part of the first split.
  • Do not rewrite all Kubernetes access to the Python client yet.
  • Do not build the multi-cluster agent yet.

Do first

  • Thin app/http.py by moving business orchestration to services.
  • Create an incident lifecycle service for dedup/create/update/resolve.
  • Keep investigation behavior unchanged but isolate its boundary.
  • Keep approval and execution separate in code, even if still same process.
  • Add tests around service boundaries before runtime changes.

Suggested first PR boundary

Start with the smallest useful extraction: incident lifecycle orchestration.

app/incidents/service.py
  - investigate_manual_target(kind, namespace, name)
  - ingest_alertmanager_target(kind, namespace, name, statuses, receiver)
  - resolve_alertmanager_target(kind, namespace, name, statuses, receiver)
  - deduplicate_active_target(kind, namespace, name)

app/http.py
  - validates request/auth
  - calls incident service
  - returns API response

This keeps the deployment unchanged but prepares the codebase for later async workers and external queues.

Future target remains possible, but not now

The modular monolith is a stepping stone. These components can later become separate deployments when needed.
